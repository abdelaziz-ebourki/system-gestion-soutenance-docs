\subsection{Introduction}
\label{ch4:intro}

Ce chapitre détaille la mise en œuvre technique du système de gestion des soutenances. Nous présentons l'environnement de développement, l'architecture logicielle détaillée, ainsi que l'implémentation des modules fonctionnels avec des extraits de code représentatifs. Un accent particulier est mis sur le moteur de détection de conflits et l'interface interactive de planification, qui constituent le cœur technique du projet. Ce chapitre représente la partie la plus dense du rapport, car il traduit la conception présentée au chapitre précédent en implémentation concrète, en justifiant chaque choix technique par les contraintes métier identifiées lors de l'analyse des besoins.

\subsubsection{Workflow de développement}
\label{ch4:workflow}

Le projet suit un workflow de développement organisé en cycles courts. Chaque fonctionnalité est développée sur une branche dédiée (\texttt{feature/*}), testée localement, puis fusionnée sur la branche \texttt{main} via une pull request. Les hooks de pré-commit (Husky + lint-staged) exécutent automatiquement le linting et le formatage avant chaque commit, veillant à ce que le code poussé soit toujours conforme aux standards de l'équipe (c.-à-d.\ les standards industriels).

La stratégie de branching est simplifiée mais efficace : la branche \texttt{main} est toujours dans un état stable et déployable, les branches \texttt{feature/*} vivent le temps du développement d'une fonctionnalité, et les branches \texttt{fix/*} sont utilisées pour les corrections de bugs. Les messages de commit suivent les conventions sémantiques : \texttt{feat:} pour les nouvelles fonctionnalités, \texttt{fix:} pour les corrections, \texttt{chore:} pour la maintenance et les résolutions des conflits de fusion, \texttt{docs:} pour la documentation, et \texttt{test:} pour les ajouts de tests.

Le pipeline \acrshort{cicd} (GitHub Actions) automatise la construction et les tests à chaque push. Trois workflows distincts couvrent les trois composants : l'\acrshort{api} est construite avec Maven (\texttt{./mvnw package}), l'\acrshort{ui} est compilée avec Vite (\texttt{npm run build}), et les tests \acrshort{e2e} s'exécutent avec Playwright contre les deux serveurs démarrés en parallèle. La synchronisation entre les dépôts est assurée par des scripts rsync qui copient les sources dans le dépôt \acrshort{e2e} lors de chaque fusion sur \texttt{main}.

\subsection{Architecture technique du système}
\label{ch4:architecture}

L'application suit une architecture web moderne et découplée (\acrshort{api} \acrshort{rest} + SPA), assurant une séparation nette entre la logique métier et la présentation, à l'exception du moteur de détection de conflits. Celui-ci est déployé côté serveur (\texttt{ConflictDetectionService}) pour garantir l'intégrité des données lors de la persistance, et dupliqué côté client (\texttt{conflict-engine.ts}) pour offrir une réactivité immédiate lors de la planification interactive. Cette duplication contrôlée permet au coordinateur de visualiser les conflits en temps réel lors du glisser-déposer dans le \textit{Defense Designer}, sans attendre la réponse du serveur, tout en assurant que la validation finale applique les mêmes six règles de gestion (RG1--RG6).

\subsubsection{Le Backend : \acrshort{api} \acrshort{rest} Spring Boot}
\label{ch4:backend}

Le backend est structuré selon un pattern en couches strict pour assurer la maintenabilité. Chaque couche a une responsabilité clairement définie et communique avec les couches adjacentes via des interfaces bien définies.

Les \textbf{endpoints \acrshort{rest}} sont exposés par la couche Contrôleur, qui gère la validation des entrées via les annotations \texttt{@Valid} et les DTOs de requête. Les contrôleurs utilisent l'injection de dépendances pour accéder aux services métier et retournent des réponses enveloppées dans \texttt{ApiResponse<T>}. Le paramètre \texttt{@AuthenticationPrincipal User user} extrait l'utilisateur courant directement depuis le contexte de sécurité Spring, sans passer par le \texttt{SecurityContextHolder}.

La \textbf{logique métier} réside dans la couche Service, où le \texttt{ConflictDetectionService} et le \texttt{ScheduleService} constituent les services centraux du module de planification. Tous héritent de \texttt{BaseCrudService<T, ID, R>} qui fournit les opérations \acrshort{crud} de base (\texttt{findAll}, \texttt{findByIdOrThrow}, \texttt{save}, \texttt{deleteWithCheck}), réduisant la duplication de code entre modules.

La \textbf{persistance des données} est assurée par la couche Repository via Spring Data \acrshort{jpa}, avec des requêtes dérivées et des \texttt{@Query} personnalisées. Aucune implémentation concrète n'est nécessaire : Spring Data génère automatiquement les requêtes à partir des noms de méthodes (par exemple, \texttt{findByEmail} produit une requête SELECT avec clause WHERE sur l'email).

Enfin, la \textbf{couche Entité} modélise les objets du domaine avec les annotations \acrshort{jpa} (\texttt{@Entity}, \texttt{@OneToMany}, \texttt{@ManyToOne}). L'héritage des utilisateurs suit la stratégie JOINED, et les données flexibles (membres de jury, coefficients) sont stockées via \texttt{@ElementCollection}.

Le projet est organisé en modules fonctionnels : \texttt{auth/} (authentification \acrshort{jwt}), \texttt{admin/} (configuration des entités académiques), \texttt{coordinator/} (cœur métier avec 11 sous-modules), \texttt{teacher/} (évaluations et indisponibilités), \texttt{student/} (consultation et documents), \texttt{notification/} (email et notifications internes), \texttt{common/} (configuration Spring Security, OpenAPI, audit, mappers, exceptions).

\subsubsection{Le Frontend : SPA React}
\label{ch4:frontend}

L'interface utilisateur est une application monopage avec les caractéristiques suivantes.

La \textbf{gestion d'état asynchrone} est assurée par \texttt{TanStack Query v5} pour la synchronisation avec l'\acrshort{api}, la mise en cache et le rechargement automatique des données. Chaque module dispose de ses propres hooks de requête (par ex.~\texttt{use-admin-queries}, \texttt{use-coordinator-queries}) qui encapsulent les appels \acrshort{api} et gèrent automatiquement le cache, les rechargements et les invalidations. Le \texttt{QueryClient} est configuré avec un \texttt{staleTime} de 30~secondes et un nombre de retry limité à 1, pour éviter les rechargements excessifs tout en autorisant une récupération rapide après une erreur réseau.

Le \textbf{routage} utilise React Router v7 avec des routes imbriquées. Les routes publiques (\texttt{/login}, \texttt{/forgot-password}, \texttt{/print/*}) sont en dehors du layout authentifié. Les routes protégées sont regroupées par rôle sous \texttt{<DashboardLayout>} avec des gardes \texttt{ProtectedRoute} qui vérifient le rôle de l'utilisateur.

Le \textbf{design system} repose sur Tailwind \acrshort{css}~4 avec des variables \acrshort{css}, shadcn/ui pour les composants de base (boutons, modales, tableaux), et des abstractions applicatives dans le répertoire \texttt{src/components/ui/}. Chaque composant \acrshort{ui} est un wrapper personnalisé qui encapsule les composants Radix UI sous-jacents avec les styles Tailwind de l'application.

Les \textbf{composants spécifiques} sont organisés par module fonctionnel dans le répertoire \texttt{src/components/}. Par exemple, le sous-répertoire \texttt{coordinator/} contient les composants \texttt{DefenseCalendar}, \texttt{DraggableJurySlot}, \texttt{JurySidebar}, \texttt{SlotRow}, \texttt{RoomSearchSelect}, etc. Cette organisation permet de localiser rapidement les composants liés à une fonctionnalité donnée.

La \textbf{validation locale} est assurée par le moteur de conflits TypeScript (\texttt{conflict-engine.ts}), une réplique fonctionnelle du moteur Java, permettant une validation instantanée sans aller-retour serveur. Les schémas de validation Zod (\texttt{validations.ts}) garantissent la conformité des données saisies par l'utilisateur avant envoi au serveur.

Le token \acrshort{jwt} est transmis et stocké via un cookie \texttt{httpOnly} (\texttt{jwt\_token}, \texttt{SameSite=Lax}, durée 2 heures) défini par le serveur lors de la connexion via l'en-tête \texttt{Set-Cookie}. Cette approche renforce la sécurité en rendant le token inaccessible aux scripts JavaScript, protégeant ainsi le système contre les attaques XSS. Le contrôle d'accès est renforcé côté serveur par Spring Security avec des annotations \texttt{@PreAuthorize} basées sur les rôles (\texttt{ROLE\_ADMIN}, \texttt{ROLE\_COORDINATOR}, \texttt{ROLE\_TEACHER}, \texttt{ROLE\_STUDENT}).

Le module gère également la réinitialisation du mot de passe : l'utilisateur demande un lien de réinitialisation via \texttt{/api/auth/forgot-password}, le système génère un token UUID avec une durée de validité de 1 heure, envoie un email contenant le lien (via Mailpit en développement ou un serveur SMTP en production), et l'utilisateur définit un nouveau mot de passe via \texttt{/api/auth/reset-password}. La validation de la force du mot de passe utilise la bibliothèque zxcvbn, qui évalue la résistance aux attaques par force brute en temps réel.

Le \texttt{JwtAuthFilter} (qui étend \texttt{OncePerRequestFilter}) intercepte chaque requête, extrait le token du header \texttt{Authorization} ou du cookie \texttt{jwt\_token}, le valide via \texttt{JwtTokenProvider}, charge l'utilisateur correspondant depuis un cache (\texttt{UserCacheService}), et configure le \texttt{SecurityContextHolder} Spring avec les autorisations appropriées. Les utilisateurs désactivés (\texttt{isActive = false}) sont bloqués avec un code 403.

\subsubsection{Le \textit{Defense Designer} : Planification Interactive}
\label{ch4:module_designer}

Le module de planification est l'élément le plus complexe du système. Il implémente une interface de type « canevas » permettant au coordinateur d'organiser les soutenances visuellement. L'architecture repose sur trois composants principaux : une barre latérale listant les jurys non planifiés, un calendrier interactif organisant les créneaux par salle et par date, et un panneau de détails affichant les informations du jury sélectionné.

L'interaction repose sur \texttt{@dnd-kit/core}, qui permet le glisser-déposer des jurys depuis la barre latérale vers les cellules du calendrier. Chaque cellule représente un couple (date, créneau horaire) pour une salle sélectionnée. Le hook \texttt{useDefenseSchedule} orchestre l'ensemble du cycle de vie. Lors du dépôt d'un jury sur un créneau, le moteur de conflits local est invoqué pour valider l'opération. En cas d'erreur, le dépôt est annulé et un message explicatif (avec suggestion de résolution) est affiché.

Les modifications du planning sont stockées dans un état React local (\texttt{useState}) avec la clé \texttt{juryId} et ne sont synchronisées avec le serveur qu'au moment de la sauvegarde explicite. Cette approche d'\textbf{état local optimiste} réduit drastiquement le nombre d'appels \acrshort{api} (un seul appel de sauvegarde au lieu d'un appel par dépôt) et améliore la fluidité perçue.

L'algorithme d'\textbf{auto-génération} parcourt itérativement les salles, les jours et les créneaux pour proposer un planning initial. Pour chaque jury non planifié, l'algorithme cherche le premier créneau disponible en vérifiant les contraintes de capacité de salle et les conflits potentiels. Le \texttt{ScheduleService.autoGenerate} côté serveur implémente la même logique avec validation des contraintes de capacité, validant que le planning généré est conforme avant persistance.

\subsubsection{Le Moteur de Détection de Conflits}
\label{ch4:module_conflicts}

L'intégrité du planning est garantie par le \texttt{ConflictDetectionService} qui exécute systématiquement six vérifications lors de chaque enregistrement. Le tableau de bord des conflits affiché au coordinateur regroupe chaque type de violation avec son niveau de sévérité.

Le même moteur est dupliqué côté client en TypeScript (\texttt{conflict-engine.ts}). La fonction \texttt{validateSlotAssignment} implémente les mêmes 6 vérifications avec des messages d'erreur en français et des suggestions de résolution intelligentes. Cette duplication permet au coordinateur de visualiser les conflits en temps réel lors du glisser-déposer dans le \textit{Defense Designer}, sans attendre la réponse du serveur.

Le moteur client inclut également une fonction \texttt{getSmartSuggestions} qui analyse le contexte pour proposer des alternatives pertinentes (salles libres, créneaux disponibles) lorsqu'un conflit est détecté, améliorant ainsi l'expérience utilisateur. Cette fonction parcourt les salles disponibles pour la date et le créneau conflictuel, filtre par capacité, et retourne la première alternative trouvée accompagnée d'un message d'explication.

\subsubsection{Module d'Évaluation et Notation}
\label{ch4:module_evaluation}

Le module d'évaluation gère la saisie des notes par les membres du jury, le calcul des moyennes pondérées et le suivi de l'avancement des évaluations. La particularité du système réside dans la \textbf{pondération dynamique} : chaque session de soutenance définit des coefficients par rôle de jury (Président, Rapporteur, Examinateur -- chacun avec un coefficient configurable) stockés dans la table \texttt{defense\_session\_coefficients}.

L'enseignant accède à la page d'évaluations (\texttt{/teacher/evaluations}) qui affiche la liste des soutenances auxquelles il est assigné en tant que membre de jury. Pour chaque soutenance, il peut saisir un score (sur 20) et un commentaire. Le statut de l'évaluation évolue de \texttt{PENDING} (en attente de saisie) à \texttt{SUBMITTED} (note soumise). Une fois la note soumise, elle ne peut plus être modifiée, maintenant l'intégrité du processus d'évaluation.

Le calcul de la moyenne pondérée est effectué par le service \texttt{CoordinatorGradeService} via la méthode \texttt{getWeightedAverage}, qui agrège les scores individuels de chaque membre et les pondère selon les coefficients de la session.

Le coordinateur peut consulter l'avancement des évaluations via la page des notes, qui affiche pour chaque soutenance le nombre d'évaluations soumises sur le nombre total attendu, avec une barre de progression visuelle. Cette vue permet d'identifier rapidement les soutenances pour lesquelles toutes les notes n'ont pas encore été saisies.

\subsubsection{Génération Documentaire et Stratégie d'Impression}
\label{ch4:module_print}

Le système supporte cinq types de documents administratifs, chacun implémenté comme un endpoint côté serveur utilisant des modèles Thymeleaf et la conversion \gls{html}-vers-\acrshort{pdf} via OpenHTMLToPDF.

La \textbf{fiche d'évaluation} (\texttt{PrintEvaluationSheet}) présente les informations du projet, du jury et de l'étudiant, avec des espaces dédiés à la saisie des notes et des observations par chaque membre du jury. La \textbf{liste de présence} (\texttt{PrintAttendanceList}) recense l'ensemble des soutenances d'une journée avec les noms des étudiants, des encadrants et des membres du jury, permettant au coordinateur de vérifier la présence physique de chaque acteur. La \textbf{convocation jury} (\texttt{PrintJuryConvocation}) est une lettre officielle adressée à chaque membre du jury, mentionnant la date, l'heure, la salle et le projet à évaluer. Le \textbf{planning imprimable} (\texttt{PrintDefenseSchedule}) présente le planning complet sous forme de tableau, organisé par salle et par créneau horaire. Enfin, le \textbf{procès-verbal} (\texttt{PrintProcesVerbal}) documente le déroulement de la soutenance avec les notes finales, la décision du jury (Admis ou Ajourné) et les signatures.

La génération de documents \acrshort{pdf} est entièrement traitée côté serveur. Le \texttt{DocumentDataService} assemble les données structurées à partir des entités \acrshort{jpa} (projets, jurys, créneaux, évaluations), puis le \texttt{DocumentGenerationService} les injecte dans des modèles Thymeleaf pour produire du \acrshort{html}. Ce \acrshort{html} est ensuite converti en \acrshort{pdf} via \texttt{OpenHTMLToPDF} (basé sur Flying Saucer), qui applique les feuilles de style dédiées au format A4. Cette architecture garantit un rendu consistant quel que soit le navigateur, sans dépendre des capacités d'impression du client.

\subsubsection{Système de Notifications}
\label{ch4:module_notifications}

Le système de notifications internes permet au système de communiquer des informations importantes aux utilisateurs sans dépendre d'un canal externe (email). Chaque notification est une entité \texttt{AppNotification} stockée en base de données avec un type (\texttt{SUCCESS}, \texttt{WARNING}, \texttt{ERROR}, \texttt{INFO}), un titre, un message, un horodatage, un statut de lecture et un lien d'action optionnel.

Les notifications sont créées automatiquement par les services métier lors d'événements significatifs : création d'une soutenance, changement de statut d'une session, détection de conflit, soumission d'une évaluation, etc. Le frontend interroge le serveur toutes les 30 secondes via le hook \texttt{useNotifications} (configurable via \texttt{NOTIFICATION\_POLL\_INTERVAL}) pour récupérer les nouvelles notifications. Le composant \texttt{NotificationBadge} dans la sidebar affiche le nombre de notifications non lues sous forme de badge rouge.

L'endpoint \texttt{POST /api/notifications/\{id\}/send-email} permet aux administrateurs et coordinateurs de déclencher l'envoi d'un email associé à une notification. En mode développement, les emails sont dirigés vers Mailpit, qui offre une interface web (\texttt{http://localhost:8025}) permettant de visualiser les emails envoyés sans nécessiter de serveur SMTP réel.

\subsubsection{Système d'Audit}
\label{ch4:module_audit}

La traçabilité des actions est assurée par un système d'audit basé sur la programmation orientée aspect (AOP). L'annotation \texttt{@Audited(action="CREATE", entity="Department")} placée sur les méthodes de service déclenche automatiquement l'enregistrement d'une entrée dans la table \texttt{audit\_log} via l'aspect \texttt{AuditAspect}.

L'aspect intercepte l'exécution de la méthode annotée, capture le résultat (succès ou échec), extrait l'identifiant de l'entité concernée (soit depuis les arguments de la méthode, soit depuis la valeur de retour via réflexion), et écrit un journal d'audit dans une transaction indépendante (\texttt{TransactionTemplate}) pour assurer l'enregistrement même en cas d'échec de la transaction métier.

Chaque entrée d'audit contient l'action effectuée (\texttt{CREATE}, \texttt{UPDATE}, \texttt{DELETE}), le type d'entité concernée, l'identifiant de l'entité, l'email de l'utilisateur ayant effectué l'action, les détails de l'opération et l'horodatage. Le coordinateur d'administration peut consulter ces journaux via la page \texttt{/admin/audit-logs}, qui offre une vue paginée et filtrable de l'ensemble des actions effectuées dans le système.

\subsubsection{Module de Configuration Administrative}
\label{ch4:module_config}

Le module d'administration gère la configuration structurelle du système à travers plusieurs entités de référence. Un singleton \texttt{DefenseSettings} fournit les paramètres globaux par défaut (horaires, durées) utilisés par le moteur de planification ainsi que les bornes de création des groupes, tandis que les réglages spécifiques à chaque session sont définis par le coordinateur.

Les entités de référence (\texttt{Level}, \texttt{Major}, \texttt{JuryRoleTemplate}) sont gérées via des interfaces \acrshort{crud} standard avec recherche et pagination. Le composant \texttt{ConfigEntityManager} est un composant réutilisable qui fournit automatiquement les dialogues de création, modification et suppression pour toute entité de référence, réduisant ainsi la duplication de code entre les différentes pages de configuration.

L'interface d'administration s'articule autour d'un tableau de bord offrant une vue d'ensemble du système : nombre d'utilisateurs, de projets, de soutenances planifiées et d'alertes en attente de traitement.

\subsection{Bonnes pratiques adoptées}
\label{ch4:bonnes_pratiques}

Le développement du système a été guidé par des bonnes pratiques industrielles visant à préserver la qualité, la maintenabilité et la reproductibilité du code.

\subsubsection{Tests automatisés}
\label{ch4:tests}

La stratégie de tests suit la pyramide des tests : un grand nombre de tests unitaires à la base, un nombre modéré de tests d'intégration au milieu, et un nombre réduit de tests de bout en bout au sommet. Côté backend, 86 classes de test JUnit 5 + Mockito couvrent les services, les contrôleurs et les utilitaires, avec une couverture de 85\% des lignes et 70\% des branches mesurée par JaCoCo. Côté frontend, 91 fichiers de test Vitest + React Testing Library couvrent les pages, les hooks, les composants et les utilitaires, avec une stratégie de mocking basée sur MSW (Mock Service Worker) qui simule les réponses de l'API sans appel réseau. Les tests E2E Playwright (environ 65 tests) valident les parcours utilisateur complets contre l'API réelle, avec une authentification préalable pour les 4 rôles.

\subsubsection{Hooks de pré-commit}
\label{ch4:hooks}

Husky et lint-staged implémentent des hooks de pré-commit qui s'exécutent automatiquement avant chaque commit Git. Pour les fichiers TypeScript/\gls{tsx}, ESLint et Prettier sont exécutés en parallèle. Pour les fichiers Java, le formatage est vérifié via SpotBugs, Checkstyle et PMD. Si l'une de ces vérifications échoue, le commit est bloqué, empêchant l'introduction de code non formaté ou contenant des erreurs de linting dans le dépôt. Cette barrière de qualité, combinée aux hooks post-commit qui exécutent les tests unitaires, constitue un filet de sécurité qui maintient la qualité du code à chaque étape du développement.

\subsubsection{Conventions Git et GitHub}
\label{ch4:git_conventions}

Les messages de commit suivent les conventions sémantiques : préfixes \texttt{feat:}, \texttt{fix:}, \texttt{chore:}, \texttt{docs:}, \texttt{test:}, suivis d'une description en anglais à l'impératif. Les pull requests documentent les changements apportés et lient les issues GitHub correspondantes. Les issues GitHub servent de support au suivi des tâches, avec des labels de priorité (\texttt{high}, \texttt{medium}, \texttt{low}) et de catégorie (\texttt{bug}, \texttt{feature}, \texttt{documentation}). Les releases GitHub documentent les versions majeures avec un changelog structuré.

\subsubsection{Pipeline \acrshort{cicd}}
\label{ch4:cicd}

Le pipeline GitHub Actions automatise la construction, les tests et la synchronisation entre les dépôts. Trois workflows distincts s'exécutent à chaque push sur \texttt{main} : le workflow de l'\acrshort{api} compile le code Java avec Maven, exécute les tests unitaires et vérifie la couverture de code. Le workflow de l'\acrshort{ui} lance le build Vite et les tests Vitest. Le workflow \acrshort{e2e} synchronise les sources, démarre les deux serveurs, et exécute les tests Playwright. La synchronisation entre les dépôts est assurée par des scripts rsync qui copient les sources dans le dépôt \acrshort{e2e}, s'assurant que les tests d'intégration s'exécutent toujours sur la dernière version du code.

\subsection{Difficultés rencontrées et solutions}
\label{ch4:difficultes}

Plusieurs difficultés techniques ont été rencontrées au cours du développement, nécessitant des solutions adaptées.

La principale difficulté a été la \textbf{synchronisation de l'état du planning} entre l'interface interactive (glisser-déposer) et la base de données. Le \textit{Defense Designer} manipule un état local complexe (associations jury $\rightarrow$ créneau) qui doit être validé contre six règles de gestion avant persistance. La solution a consisté à utiliser un \textbf{état local optimiste} dans le hook \texttt{useDefenseSchedule}, qui ne synchronise le serveur qu'au moment de l'enregistrement final. Cette approche réduit drastiquement le nombre d'appels \acrshort{api} (un seul appel de sauvegarde au lieu d'un appel par dépôt) et améliore la fluidité perçue.

Une seconde difficulté a été la \textbf{duplication du moteur de conflits} entre Java et TypeScript. Pour assurer la cohérence, les deux implémentations suivent exactement la même séquence de vérifications et les mêmes structures de données (projet, salle, enseignant, indisponibilité). Les tests unitaires des deux moteurs valident les mêmes scénarios, et les messages d'erreur sont maintenus de manière cohérente entre les deux implémentations.

Une troisième difficulté a été la \textbf{conception du système de templates de jurys}. Les départements ont des besoins différents en termes de composition de jury (certains exigent un Président, un Rapporteur et un Examinateur, d'autres ajoutent un Co-encadrant). La solution a été d'implémenter des \texttt{JuryRoleTemplate} configurables par le coordinateur, chaque template définissant les rôles nécessaires, le nombre de membres par rôle et le coefficient associé. Cette flexibilité permet au système de s'adapter à différents contextes sans modification du code.

La quatrième difficulté concernait la \textbf{génération de documents \acrshort{pdf}}. Les cinq types de documents (convocation étudiant, convocation jury, fiche d'évaluation, liste de présence, procès-verbal) devaient produire des formats A4 structurés avec un rendu consistant. La solution retenue est la génération côté serveur : le \texttt{DocumentDataService} assemble les données à partir des entités \acrshort{jpa}, le \texttt{DocumentGenerationService} les injecte dans des modèles Thymeleaf, et \texttt{OpenHTMLToPDF} (basé sur Flying Saucer) convertit le \acrshort{html} en \acrshort{pdf} avec les feuilles de style dédiées. Cette architecture garantit un rendu identique quel que soit le navigateur, contrairement à une approche client \texttt{@media print} qui présente des incompatibilités entre Chrome, Firefox et Safari.

La cinquième difficulté concernait le \textbf{suivi des tâches et la collaboration} entre les membres de l'équipe de développement. Avec trois dépôts distincts (\acrshort{api}, \acrshort{ui}, \acrshort{e2e}) et des fonctionnalités à coordonner, il fallait un outil léger et intégré au workflow existant. Les solutions de gestion de projet (Jira, Trello, Notion) impliquaient une surcharge configurationnelle disproportionnée pour un projet de cette envergure. La solution retenue fut d'utiliser directement \texttt{GitHub Issues} comme canal unique de suivi : chaque tâche est documentée dans une issue étiquetée par priorité et catégorie, les pull requests referment automatiquement les issues correspondantes, et le tableau GitHub fournit une visibilité en temps réel sur l'avancement. Cette approche minimale élimine la friction outillage tout en maintenant une traçabilité complète des décisions et des modifications.

\subsection{Conclusion}
\label{ch4:conclusion}

Ce chapitre a présenté la traduction technique de la conception. L'utilisation d'une architecture découplée (\acrshort{api} \acrshort{rest} + SPA React), d'un moteur de conflits rigoureux implémenté en Java et dupliqué en TypeScript pour la réactivité, et d'une interface utilisateur moderne basée sur Tailwind \acrshort{css} et shadcn/ui, a permis de répondre aux exigences de fiabilité et d'ergonomie fixées. Les modules de notifications, d'audit et de configuration administrative complètent le système en offrant les fonctionnalités transverses nécessaires à un usage productif. Les bonnes pratiques adoptées (tests automatisés, hooks de pré-commit, conventions Git, pipeline \acrshort{cicd}) garantissent la maintenabilité du code à long terme. Le système est désormais prêt pour la phase de validation qui sera détaillée au chapitre suivant.
