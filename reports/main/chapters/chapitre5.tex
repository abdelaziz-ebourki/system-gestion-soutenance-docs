\section{Stratégie de test et validation}
\label{ch5}

\subsection{Introduction}
\label{ch5:intro}

Ce chapitre présente la démarche de validation mise en œuvre pour préserver la fiabilité du système. Les données manipulées -- notes, jurys, plannings -- ont une incidence directe sur le parcours académique des étudiants. Une erreur de planification peut priver un étudiant de sa soutenance, une erreur de calcul de moyenne peut fausser une décision de jury, et un bug de sécurité peut exposer des données confidentielles. Nous avons donc adopté une stratégie de test pyramidale multi-couche, combinant tests unitaires, d'intégration et tests de bout en bout (\acrshort{e2e}), pour détecter les régressions à chaque niveau avec un rapport coût-efficacité optimal.

\subsection{Stratégie de test}
\label{ch5:strategie}

La stratégie repose sur la validation progressive de chaque couche du système, depuis la logique métier isolée jusqu'au parcours utilisateur complet. Cette approche en pyramide -- beaucoup de tests unitaires rapides à la base, un nombre modéré de tests d'intégration au milieu, et un nombre réduit de tests \acrshort{e2e} au sommet -- offre le meilleur compromis entre couverture, vitesse d'exécution et coût de maintenance.

\subsubsection{Tests unitaires et d'intégration (Backend)}
\label{ch5:backend_tests}

Le backend Java contient \textbf{\metric{ClassesBackend} classes de test} (\metric{TestsBackend} tests unitaires et d'intégration) réparties dans le répertoire de tests du backend, calqué sur la structure du code source. Chaque module fonctionnel dispose de son propre ensemble de tests : \texttt{auth/}, \texttt{admin/}, \texttt{coordinator/}, \texttt{teacher/}, \texttt{student/}, \texttt{notification/} et \texttt{common/}.

Les tests sont réalisés avec \textbf{JUnit 5} et \textbf{Mockito}, et se concentrent sur deux axes complémentaires. Les tests unitaires des services isolent chaque service métier avec mock des dépendances (repositories, autres services), permettant de valider la logique de calcul, les règles de gestion et la gestion des erreurs sans aucune interaction avec la base de données. Les tests d'intégration des contrôleurs, réalisés via \texttt{@WebMvcTest}, testent les endpoints \acrshort{rest} avec le contexte Spring complet, validant la conformité des contrats (statuts \acrshort{http}, format \acrshort{json}), la sérialisation des DTOs, la gestion des erreurs (exceptions métier, validation échouée) et la sécurité (accès refusé pour les rôles non autorisés). Le rapport de couverture est présenté dans~\cref{fig:api-coverage}.

Parmi les classes de test notables, \texttt{ConflictDetectionServiceTest} constitue la suite la plus importante. Elle valide exhaustivement chacune des \metric{ReglesGestion} règles de gestion (RG1--RG6) avec des jeux de données spécifiques couvrant les cas nominaux (pas de conflit), les cas limites (conflit exact à la frontière d'un créneau), et les cas d'erreur (conflit multiple). Chaque test suit le pattern Arrange--Act--Assert : préparation des données de test (projets, salles, enseignants, indisponibilités), exécution de la méthode de vérification, et vérification du résultat (liste de conflits vide ou non vide selon le cas testé).

Les autres classes de test couvrent l'ensemble des modules : \texttt{AuthServiceTest} valide le cycle de vie de l'authentification (login, activation, reset), \texttt{ScheduleServiceTest} teste la logique de planification et d'auto-génération, \texttt{JuryServiceTest} teste la constitution des jurys et de la gestion des membres, \texttt{CoordinatorDefenseSessionServiceTest} teste le cycle de vie des sessions, \texttt{DocumentDataServiceTest} teste la génération des données documentaires, \texttt{NotificationServiceTest} teste le système de notifications internes, et \texttt{StudentDocumentServiceTest} teste la logique d'accès aux documents côté étudiant.

La couverture de code est monitorée via \textbf{JaCoCo (v0.8.15)} avec les objectifs suivants : couverture minimale de \metric{CouvertureLignesBackCible} sur les lignes de code et \metric{CouvertureBranchesBackCible} sur les branches conditionnelles. La couverture actuelle mesurée s'établit à \metric{CouvertureLignesBackActuel} pour les lignes et \metric{CouvertureBranchesBackActuel} pour les branches, en dessous des seuils cibles en raison de l'évolution récente du code ; l'ajout de tests de rattrapage est en cours pour atteindre ces objectifs. Les exclusions portent sur les DTOs, les entités JPA (structures de données pures sans logique), les classes de configuration Spring et le code de seed (peuplement initial de la base de démonstration). Le rapport de couverture est généré en \acrshort{html} et en XML, ce dernier étant consommé par les outils de CI pour vérifier les seuils automatiquement.

Les vérifications de qualité statique complètent les tests. \textbf{Checkstyle} vérifie la conformité du code aux conventions de codage Java (nommage, indentation, longueur des lignes, imports). \textbf{PMD} détecte les problèmes de qualité de code (code mort, duplication, complexité cyclomatique excessive, variables non utilisées). \textbf{SpotBugs} analyse le code bytecode pour identifier les bugs potentiels (pointeurs nuls, fuites de ressources, problèmes de thread safety). Ces trois outils sont intégrés au build Maven via les plugins \texttt{maven-checkstyle-plugin}, \texttt{maven-pmd-plugin} et \texttt{spotbugs-maven-plugin}, et s'exécutent automatiquement lors de chaque \texttt{mvn verify}.

\subsubsection{Tests de l'interface utilisateur (Frontend)}
\label{ch5:frontend_tests}

Le frontend TypeScript utilise \textbf{Vitest (v4.1.7)} avec \textbf{React Testing Library} et \textbf{jsdom} pour l'environnement DOM simulé. La suite de tests frontend comprend \textbf{\metric{FichiersFrontend} fichiers de test} (\metric{FichiersTestTSX} \texttt{*.test.tsx} + \metric{FichiersTestTS} \texttt{*.test.ts}), organisés dans le répertoire \texttt{src/test/} qui reproduit la structure de \texttt{src/}.

L'architecture de mocking repose sur \textbf{MSW (Mock Service Worker) v3}, qui intercepte les appels réseau au niveau du service worker du navigateur simulé. Le serveur MSW est configuré dans le fichier de setup des mocks et démarre automatiquement avant chaque test via le setup global. Les handlers de mock fournissent des réponses simulées pour l'ensemble des endpoints \acrshort{api} (auth, admin, coordinator, teacher, student). Le module registry expose des helpers de haut niveau : \texttt{mockJson} pour les réponses simples, \texttt{mockPaginated} pour les réponses paginées, \texttt{mockCrud} pour les opérations \acrshort{crud} complètes, et \texttt{mockEcho} pour retourner le corps de la requête (utile pour tester les mutations).

Le composant utilitaire \texttt{src/test/utils.tsx} fournit \texttt{renderWithProviders}, une fonction qui enveloppe tout composant testé dans les providers nécessaires : \texttt{QueryClientProvider} (TanStack Query), \texttt{MemoryRouter} (React Router), \texttt{AuthProvider} (contexte d'authentification) et \texttt{TooltipProvider} (shadcn/ui). Cette abstraction élimine la duplication de configuration entre les tests et assure un environnement de test cohérent.

Les tests couvrent \metric{CategoriesComposants} catégories de composants. Les hooks personnalisés sont testés via des composants « harness » qui les appellent dans un contexte React contrôlé. Les composants \acrshort{ui} (DefenseCalendar, DraggableJurySlot, JurySidebar, AvailabilityCalendar, ProjectDialog) sont testés pour leur rendu, leurs interactions et leur état. La validation (conflict-engine.test.ts) est testée unitairement pour valider la cohérence avec le moteur Java. Le routage (ProtectedRoute) est testé pour les redirections selon les rôles. Enfin, chaque page de l'application dispose d'un test de rendu validant la présence des éléments clés. La couverture obtenue est détaillée dans~\cref{fig:ui-coverage}.

\subsubsection{Tests de bout en bout (\acrshort{e2e})}
\label{ch5:e2e_tests}

La validation finale du système est confiée à \textbf{Playwright (v1.52)}, qui simule des interactions réelles dans un navigateur Chromium. Contrairement aux tests unitaires et d'intégration qui tournent contre des mocks, les tests \acrshort{e2e} s'exécutent contre l'\acrshort{api} Spring Boot réelle et la base de données H2, assurant une fidélité maximale aux comportements de production.

L'architecture repose sur le pattern \textbf{setup-project} de Playwright. Le fichier \texttt{auth.setup.ts} s'exécute une seule fois avant tous les tests et authentifie les \metric{RolesUtilisateurs} rôles (admin, coordinateur, enseignant, étudiant) en remplissant le formulaire de connexion et en soumettant les credentials. Le contexte de navigateur résultant (cookies \acrshort{jwt}) est sérialisé dans des fichiers \acrshort{json} (\texttt{.auth/admin.json}, etc.) et réutilisé via l'option \texttt{storageState} de chaque bloc \texttt{test.describe}. Cette approche élimine la phase de connexion pour chaque test, réduisant le temps d'exécution et la fragilité liée aux changements d'interface de connexion.

Les tests \acrshort{e2e} sont organisés en \metric{FichiersE2E} fichiers de test, chacun ciblant un rôle ou un flux spécifique : \texttt{auth.spec.ts} teste le cycle de connexion (succès, échec, déconnexion, reset MDP, activation), \texttt{admin.spec.ts} teste le \acrshort{crud} des départements, salles et utilisateurs, \texttt{coordinator.spec.ts} teste la création et transition des sessions ainsi que la gestion des projets, \texttt{teacher.spec.ts} teste la saisie des indisponibilités et des évaluations, \texttt{student.spec.ts} teste la consultation du groupe et des documents, \texttt{audit-logs.spec.ts} vérifie l'accès aux journaux d'audit par rôle sur l'ensemble des routes, et \texttt{system.spec.ts} teste les notifications et le responsive design.

La configuration Playwright utilise un worker unique (\texttt{workers: 1}) et le parallélisme désactivé (\texttt{fullyParallel: false}), car les tests s'exécutent contre une base de données H2 partagée dont l'état est modifié par chaque test. Les tentatives de rejeu sont désactivées en développement (0) et activées en CI (2). Les traces et captures d'écran ne sont conservées qu'en cas d'échec, pour faciliter le diagnostic sans encombrer l'espace disque.

Le pipeline CI (\texttt{.github/workflows/e2e-tests.yml}) automatise l'exécution : les jobs \texttt{build-api} et \texttt{build-ui} construisent les artefacts en parallèle, puis le job \texttt{e2e} les télécharge, démarre les deux serveurs avec health-check loops, exécute les tests Playwright, et génère le rapport \acrshort{html}. Ce pipeline s'exécute à chaque fusion sur la branche \texttt{main} et s'assure que les tests d'intégration s'exécutent toujours sur la dernière version du code.

\subsubsection{Tests d'API (Postman)}
\label{ch5:postman_tests}

En complément des tests automatisés, une collection Postman de \textbf{\metric{RequetesPostman} requêtes} couvre l'ensemble des endpoints \acrshort{rest} de l'API. Organisée par module fonctionnel (auth, admin, coordinator, teacher, student, common), elle permet de valider manuellement les contrats d'interface et de servir de documentation exécutable pour l'équipe. Les tests Postman incluent des assertions sur les statuts \acrshort{http}, la structure \acrshort{json} des réponses et les scénarios de bout en bout. \subsection{Évaluation globale et limites}
\label{ch5:evaluation}

Le système répond aux exigences fonctionnelles du cahier des charges. La détection automatique des conflits réduit drastiquement le temps de planification et élimine les erreurs humaines. L'intégration des tests dans le pipeline CI garantit la non-régression des fonctionnalités critiques lors de chaque modification du code. La pyramide de tests -- \metric{TestsBackend} tests Java (\metric{ClassesBackend} classes), \metric{TestsFrontend} tests TypeScript (\metric{FichiersFrontend} fichiers), \metric{RequetesPostman} requêtes Postman -- offre une couverture à chaque niveau de l'application.

Cependant, certaines limites subsistent et méritent d'être documentées. La couverture \acrshort{e2e}, bien que fonctionnelle, ne couvre pas encore l'intégralité des cas limites et des parcours utilisateurs complexes, notamment les scénarios de rattrapage et les flux d'erreur (serveur indisponible, token expiré). La génération de \acrshort{pdf} côté serveur via OpenHTMLToPDF garantit un rendu identique quel que soit le navigateur, mais le support limité des fonctionnalités \acrshort{css} modernes (flexbox, grilles) dans le moteur Flying Saucer peut contraindre la complexité des mises en page possibles. Une évolution vers iText ou Puppeteer est envisagée pour des layouts plus sophistiqués.

L'auto-génération propose un planning initial que le coordinateur peut ajuster via le \textit{Defense Designer}. Cette fonctionnalité d'assistance réduit le temps de planification tout en laissant au coordinateur la maîtrise finale de l'organisation.

Le système ne supporte actuellement ni les mises à jour en temps réel (WebSocket) ni le mode hors ligne. Les notifications nécessitent un rechargement périodique (toutes les \metric{PollingSecondes} secondes), et les données du planning ne sont accessibles qu'en ligne. Enfin, l'utilisation de H2 en base de données de développement, bien que pratique pour les tests et le seed data, ne reproduit pas fidèlement toutes les fonctionnalités de \acrshort{mysql} (notamment les requêtes géospatiales et les index composites), ce qui peut masquer des problèmes de performance en production.

\subsection{Conclusion}
\label{ch5:conclusion}

La stratégie de test multi-couche a permis d'aboutir à une application stable et fiable. Les \textbf{\metric{TestsTotalAuto} tests automatisés} (unitaires et d'intégration) complétés par \textbf{\metric{RequetesPostman} scénarios de validation \acrshort{api} via Postman} couvrent l'ensemble des fonctionnalités critiques. L'intégration des outils de qualité (JaCoCo, Checkstyle, PMD, SpotBugs, ESLint, Prettier) dans le pipeline Maven et les hooks Husky assure la pérennité de la qualité du code au fil des évolutions futures.
